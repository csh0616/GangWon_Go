## 1. 프로젝트 개요

- **목표**: 2026 관광데이터 활용 공모전 웹·앱 개발 부문 최종 데모 제출 (D-Day: 9/21)
- **서비스명**: GANGWON GO — AI Agent 기반 강원도 외국인 관광객 맞춤형 여행 플래닝 & 실시간 매니징
- **핵심 차별점**: 플래닝(요청 시 코스 생성) + 매니징(조건 변화 시 능동 개입)을 분리된 레이어로 구현
- **타겟 사용자**: 강원도 방문 외국인 관광객
- **데모 언어**: 영어, 중국어 우선 (2개만 실제 구현). 제안서의 "6개 언어" 문구는 발표 화법으로만 대응 — 11.1절
- **데모 대상 시군**: 인제·홍천·평창 (제안서의 강원 특화 카테고리 중 소도시·지역축제·스키장/윈터 3개와 겹치는 조합 — 11.5절). **확정 아님** — 팀 판단에 따라 다른 시군으로 교체 가능. 교체 시 이 줄, 2.1절 수용기준, 8장 마일스톤의 시군명만 갱신하면 되고 파이프라인(3.5절)은 시군에 무관하게 동일하게 동작
- **데모 방식**: 웹 기반 PWA, QR/링크 접속, 라이브 데모는 포그라운드(WebSocket) 시나리오 중심

## 2. 범위 정의 (반드시 지킬 것)

### 2.1 데모에서 실제 구현 (Must-have)

| 기능 | 구현 내용 | 수용 기준 |
|---|---|---|
| AI 맞춤형 코스 추천 | 입력을 2트랙으로 분리: **① 구조화 입력(필수, 폼으로 직접 입력)** — 날짜, 인원, 관계(동행 유형). **② 자유 텍스트(어떤 여행을 원하는지)** — LLM이 여기서만 interest/activity_level 등 주관적 파라미터를 추출. 객관적 값은 LLM 파싱을 거치지 않고 그대로 사용 → DB 조회 + 클러스터링+2-opt로 알고리즘이 코스 생성 → **LLM은 완성된 코스의 자국어 내레이션만** 추가 (코스 구조 자체는 LLM이 만들지 않음, 지연시간·비용·오탐 위험 절감 목적) | 인제/홍천/평창 대상, 3초 이내 코스 생성 완료. 날짜·인원·관계 미입력 시 생성 요청 자체가 막힘(필수값) |
| 실시간 매니징 | node-cron 스케줄러(5~10분 주기) + 규칙 기반 트리거 + Supabase Realtime push. **2단계 확인 흐름** — ① 트리거 조건에 걸리는 스탑을 찾아 상황에 맞게 조정한 가중치(3.5절)로 대체 후보 1개를 미리 계산해 "제안"만 알림으로 보냄(itinerary_json은 아직 안 바뀜) ② 사용자가 Yes를 눌러야 그 스탑만 실제로 교체되고 해당 날짜만 2-opt 재정렬. No를 누르면 아무것도 안 바뀜 | 트리거 후 3초 이내 확인 모달(질문형 문구 — "비가 옵니다, [야외 스탑] 대신 [대체 장소]로 변경할까요?" 형태. 장소명은 예시이며 실제로는 데모 시드 데이터에 있는 실제 POI명 사용, 8장/11.5절) 표시. Yes 클릭 후 3초 이내 해당 스탑만 교체 반영(코스 전체가 다시 그려지지 않음) |
| 다국어 정밀 지도 | 카카오맵 JS SDK + 2개 언어(영/중) UI + **내 위치 표시**(파란점, `navigator.geolocation`으로 페이지가 열려있는 동안만 갱신 — 서버로 전송·저장하지 않는 순수 클라이언트 기능. 위치 거부/미지원 시 마커 없이 코스만 표시, 6장 폴백과 동일 원칙) | 지도 마커, 경로선, 언어 전환, 내 위치 표시 정상 동작 |
| 여행 케어 안내 | 정적 큐레이션(의료시설/응급연락처) + SOS 버튼(사용자 트리거 방식, tel:119) | 데모 시군 기준 의료 데이터 최소 5건, SOS 클릭 시 tel:119 연결 확인. **로그인 여부와 무관하게 항상 접근 가능** (안전 기능이므로 가입 장벽 없음) |
| 게스트 체험 → 저장 시 간편 로그인 | 코스 생성·조회는 로그인 없이 이용(서버에 유저 row 없음, 코스는 클라이언트 상태로만 존재). "코스 저장" 버튼 클릭 시 Google 로그인(3.9절) 팝업 → 로그인 완료 시 `users`+`itineraries` row가 동시 생성되며 해당 일정이 매니징 감시 대상으로 등록됨 | 로그인 없이 코스 생성 3초 이내 완료, 저장 버튼 클릭 후 로그인 완료 시 3초 이내 "저장됨"으로 전환, 이후 강제 트리거 시 매니징 알림 정상 수신 |
| 코스 부분 수정(사용자 직접) | 저장된 코스의 스탑 하나를 골라 "이 장소 바꾸기" 클릭 → 텍스트박스에 원하는 걸 자유롭게 적으면 LLM이 그 스탑에 한해 파싱(3.5절 부분 재구성) → 대체 후보 최대 3개 제시 → 선택 시 확정. 전용 엔드포인트 사용 (`POST /api/itineraries/regenerate-stop`, API_CONTRACT.md §3) — 매니징 트리거는 같은 스코어링 로직을 쓰지만 확인 절차(Yes/No) 때문에 별도 경로(`POST /api/alerts/trigger`)를 탄다. 둘이 엔드포인트를 공유하는 게 아니라 **알고리즘 로직만 같은 원리**를 공유한다는 점에 주의 (혼동하기 쉬운 지점) | 후보 제시까지 3초 이내, 선택 후 저장까지 3초 이내. 텍스트 비우고 "다시 추천"만 눌러도 동작(이 경우 원래 코스의 가중치 재사용) |

## 3. 기술 스택 (확정)

- **프론트엔드**: Next.js + Tailwind CSS (반응형: 모바일/데스크톱 2단 브레이크포인트)
- **UI 컴포넌트**: shadcn/ui (Tailwind 기반이라 추가 통합 비용 없음, 1주차부터 바로 사용 가능 — 프론트팀 임의 변경 가능)
- **다국어(i18n)**: next-intl (Next.js App Router 공식 권장 조합, EN/ZH 2개 로케일만 사용 — 1.1절)
- **백엔드**: Node.js + Express
- **DB / Realtime / 스케줄러**: Supabase (PostgreSQL, Realtime, pg_cron 또는 node-cron)
- **지도**: 카카오맵 JavaScript SDK
- **AI**: Claude API (확정, 3.7절) — 구조화 출력(tool use)으로 가중치 추출·내레이션 생성
- **인증**: Supabase Auth (간편 로그인, 3.9절)
- **배포**: 프론트 Vercel / 백엔드+에이전트 Railway 또는 Render
- **외부 데이터**: 한국관광공사 TourAPI, 의료관광정보 서비스 (5장 참고), 기상청 단기예보 API, 공공데이터포털
- **경로 최적화 거리 계산 (이원화, 확정)**: "순서 결정"과 "실제 동선 표시"에 서로 다른 방식을 쓴다.
  - **순서 결정(2-opt 내부 스코어링)**: Haversine(직선거리) 공식. 로컬 연산이라 호출 제한·지연시간 없이
    스탑이 몇 개든 자유롭게 비교 가능. 2-opt는 절대 거리가 아니라 "어떤 순서가 더 나은가"의 상대
    비교라 근사치로도 충분 (3.5절 부분 재구성 로직에도 동일 적용)
  - **실제 동선 표시(지도에 그려지는 선, 이동시간/거리 UI)**: 카카오모빌리티 Directions API(자동차
    길찾기, 5장)를 순서가 이미 정해진 뒤 **인접한 두 스탑끼리 1:1로만** 호출 (다중경유지 아님 — 백엔드팀이
    실사용 중 확인한 바로는 다중경유지 API는 한 번에 5개 초과 시 실패하고, 쪼개서 넣으면 각 구간이
    서로를 모른 채 최적화돼 동선이 지저분해지는 문제가 있었음). 순서는 이미 우리 알고리즘이 정하므로
    이 방식엔 그 문제가 발생하지 않음. 하루 스탑이 N개면 (N-1)번 호출, 무료 쿼터(1만 건/일) 내에서 충분.
    부분 재구성으로 스탑 하나만 바뀔 때도 영향받는 구간 2개만 재호출 (해당 날짜 전체 재호출 불필요)
  - 위 이유로 산간지형 우회 문제(직선거리와 실제 도로거리 편차)는 "순서"에는 근사치로 남지만,
    사용자에게 보이는 최종 지도상 동선은 실제 도로 기준이라 자연스럽게 나옴

## 3.5 코스 생성 파이프라인 (중요: LLM은 양 끝에만 사용)

LLM이 코스 전체를 추론하지 않는다. 실제 코스 구조는 DB 조회 + 알고리즘이 만든다. 입력도 객관적 값과
주관적 값을 분리해서, LLM이 파싱을 틀릴 수 있는 객관적 값(날짜/인원/관계)은 애초에 LLM에 맡기지 않는다.

1. 사용자 입력 — 2트랙
   - 구조화 입력(폼, 필수): `region_code`(시군 **단일 선택** — 인제/홍천/평창 중 하나를 카드 또는 드롭다운으로
     고름. 여러 시군을 묶은 여행은 이번 데모 범위 밖 — API에는 `region_codes` 배열로 전달하되 항상
     1개만 담는다, 추후 다중 시군 확장을 대비한 필드명 유지), `start_date`, `end_date`, `companions`(인원 수),
     `relationship`(동행 유형 enum)
   - 자유 텍스트(선택, "어떤 여행을 원하는지"): 흥미·분위기·활동 강도 등 주관적 묘사
2. LLM 파라미터 추출 (짧은 호출): `free_text` + **카테고리 마스터 목록(JSON, 아래)** 을 함께 전달 →
   LLM은 자유 문자열이 아니라 이 목록의 키에 대해서만 0~1 가중치로 응답 (`activity_level`도 함께 반환) —
   구조화 입력값(시군/날짜/인원/관계)은 이 단계에 넣지 않고 그대로 다음 단계로 전달
3. DB 조회 + 알고리즘 (LLM 미사용): 선택된 `region_code`로 후보 POI 범위를 먼저 좁히고,
   `pois.tags[]`(같은 마스터 목록 키 사용)와 가중치를 매칭해 스코어링 → `relationship` 필터(예:
   `family_with_kids`면 성인 전용 성격의 POI 태그 제외 등, 세부 매핑은 백엔드팀이 `/scripts/sync`
   구현 시 확정) → `activity_level`로 하루 스탑 개수 결정(**low: 2~3개, medium: 3~4개, high: 4~5개** —
   숫자가 많을수록 이동시간이 늘어나므로, `activity_level`은 코스 스타일이 아니라 하루 일정 밀도를
   조절하는 값으로 사용) → 일자별 클러스터링 → 클러스터 내부 2-opt로 순서 최적화(경로 최적화 방식은
   3장 참고).
   **`festival_event`는 다른 6개 카테고리와 처리 방식이 다르다** — 나머지는 상시 존재하는 장소에 대한
   선호도 점수지만, 축제는 기간 한정이라 가중치 이전에 "여행 날짜(`start_date`~`end_date`)와 겹치는 축제가
   해당 시군에 있는가"부터 필터링해야 한다. 겹치는 축제가 있고 가중치도 높으면 해당 일자의 앵커 스탑으로
   우선 배치 후 나머지 코스를 그 주변으로 클러스터링. 겹치는 축제가 없으면 가중치와 무관하게 0으로 취급
   (에러 아님, 나머지 카테고리로 자연스럽게 채움)
   > **날짜 판정은 "여행 기간"이 아니라 "그 일자" 기준이다 (수정 — 1주차 아키텍처 점검에서 발견)**:
   > 위 "여행 날짜와 겹치는가"는 후보를 1차로 추릴 때 쓰는 조건이고, **실제 배치 단계에서는 그 축제가
   > 배치될 일자(day N의 날짜)가 `event_start_date`~`event_end_date` 안에 들어가는지를 다시 확인**한다.
   > 앵커로 뽑히지 않은 축제 POI가 일반 스탑처럼 아무 날짜에나 배치되면, 사용자는 축제를 하지도 않는
   > 날에 축제장에 가게 된다(예: 9/10~9/19 축제가 9/21 일자에 배치). 앵커 경로든 일반 스탑 경로든
   > `festival_event` 태그를 가진 POI는 항상 이 일자 단위 검사를 통과해야 배치된다.
   >
   > **앵커 주변을 채울 때도 가중치를 무시하지 않는다**: 앵커가 정해진 날의 나머지 스탑은 "앵커에서
   > 가까운 순"만으로 뽑는 게 아니라, 다른 날과 동일하게 **가중치 스코어를 1차 기준으로 하되 앵커와의
   > 거리를 함께 고려**해서 고른다. 거리만 보면 사용자가 말한 취향(온천 0.9 등)이 그 날 통째로
   > 무시되고, 앵커 근처 POI가 먼저 소진되어 다른 날의 후보 품질까지 떨어진다.
   > `companions`/`relationship`은 저장 시 `itineraries`에 함께 저장한다(4장) — 매니징 자동 교체·수동
   > 편집의 부분 재구성(아래)이 이 필터를 다시 적용할 때 원본 입력을 참조할 수 있어야 하기 때문. 저장
   > 전(게스트 상태)에는 클라이언트가 들고 있다가 저장 시 `preference_weights`와 함께 그대로 전달한다.
4. 완성된 코스 데이터 (JSON)
5. (선택) LLM 자국어 내레이션: 완성된 코스에 설명 문장만 추가

**부분 재구성 (신규 — 1~5와 별개 경로)**: 코스 전체를 다시 만들지 않고 스탑 하나만 바꾸는 경로.
두 곳에서 재사용된다 — (a) 매니징 트리거가 문제 조건에 걸리는 스탑을 자동으로 찾아 호출, (b) 사용자가
"이 장소 바꾸기"를 직접 클릭 (Must-have. 텍스트박스에 원하는 걸 적으면 LLM이 그 스탑에 한해 파싱).

1. **대상 스탑 확정 (확정 — 실시간 GPS로 "사용자가 지금 어디 있는지" 추적하지 않는다는 전제 위의 규칙)**
   - 수동 편집: 사용자가 화면에서 직접 고른 스탑 (`day` + `target_poi_id`를 클라이언트가 그대로 전송,
     API_CONTRACT.md §3 `regenerate-stop`)
   - 매니징 자동 트리거(조건 감시 cron, 5~10분 주기): 그날 스탑 배열을 순서대로 훑으며 조건별로
     대상을 찾는다 — `rain`은 아직 지나지 않은 스탑 중 야외 성격 카테고리(nature_hiking/leisure_sports/
     festival_event)를 가진 첫 스탑. `traffic`은 그날 인접한 스탑 쌍(스탑1→스탑2, 스탑2→스탑3...)의
     이동시간을 전부 확인해(3장, 카카오모빌리티 Directions API) 1시간을 넘는 첫 구간을 찾고, **그
     구간의 뒤쪽 스탑**을 교체 대상으로 삼는다. "아직 지나지 않은 스탑"은 실시간 위치가 아니라 그냥
     그날 스탑 순서상의 위치를 뜻하며(방문 완료 여부를 실시간으로 추적하지 않음), 대상은 항상 그날
     첫 스탑부터 순서대로 찾는다.
   - **traffic 재선정의 기준점("현재 위치")**: 교체 대상 스탑 바로 **이전** 스탑의 좌표. 대상이 그날의
     첫 스탑이면(이전 스탑이 없으면) 그 스탑 자신의 좌표를 기준점으로 사용한다.
   - 데모 전용 강제 트리거 버튼(`POST /api/alerts/trigger`)은 위 자동 스캔 대신 `day`+`target_poi_id`를
     요청에 직접 지정한다(`regenerate-stop`과 동일한 필드) — 리허설마다 항상 같은 스탑을 겨냥해야
     하므로 스캔 로직에 의존하지 않고 결정론적으로 동작해야 함 (API_CONTRACT.md §3)
2. **가중치 결정** — 세 가지 경로:
   - 매니징 트리거(자동): `itineraries.preference_weights`(4장)에 **상황별 조정**을 적용. 예를 들어
     `condition: rain`이면 `nature_hiking`/`leisure_sports`/`festival_event`처럼 야외 성격 카테고리의
     가중치를 대폭 낮추거나 0으로 만들고 나머지는 원래 값 유지 (아래 조정표). 즉 "온천 좋아하는
     사람"이라는 원래 취향은 유지하되, 지금 상황에 안 맞는 카테고리만 눌러준다.
   - 수동 편집, 텍스트 없이 "다시 추천"만 누른 경우: 조정 없이 원래 `preference_weights` 그대로 재사용
   - 수동 편집, 텍스트를 입력한 경우: 2단계(LLM 파라미터 추출)와 **같은 스키마**를 그 텍스트 하나에만
     적용해 이 스탑 전용 가중치를 새로 뽑고, 이걸로 대체(원래 가중치는 무시)
3. 같은 날짜·같은 시군의 후보 POI 중 이미 코스에 쓰인 POI를 제외하고, `itineraries`에 저장해둔
   `relationship` 필터(1단계와 동일 기준)와 **축제 날짜 필터**를 다시 적용한 뒤 위 가중치로 재스코어링 →
   상위 1개(자동) 또는 상위 3개(수동, 사용자가 고르게) 추출
   > **축제 날짜 필터도 여기서 다시 적용해야 한다 (수정 — 1주차 아키텍처 점검에서 발견)**: 후보 풀에
   > `festival_event` 태그를 가진 POI가 있으면, **교체 대상 스탑이 속한 그 날짜**가 해당 축제의
   > `event_start_date`~`event_end_date` 안에 있는 경우에만 후보로 남긴다. 이 필터가 없으면 이미 끝난
   > 축제가 대체 후보 1순위로 제안될 수 있다(특히 `festival_cancelled` 트리거의 대체 후보로 다른 끝난
   > 축제가 나오는 경우). 코스 최초 생성(위 3단계)과 부분 재구성 양쪽 모두 같은 기준을 쓴다.
4. **매니징 트리거는 여기서 바로 적용하지 않는다** — 계산한 후보 1개를 "제안"으로만 `alerts`에 저장하고
   알림을 보낸다(itinerary_json 아직 안 바뀜). 사용자가 Yes를 눌러야 5~6단계 진행. No면 종료(itinerary_json
   그대로, `alerts` row는 dismissed로 표시). 수동 편집(사용자가 이미 직접 고른 경우)은 이 단계 없이 바로 진행.
   **중복 방지**: `alerts`에 저장하기 전, 같은 `itinerary_id`+`day`+`previous_poi_id` 조합으로
   `status='proposed'`인 row가 이미 있는지 확인 — 있으면 새로 만들지 않고 넘어간다 (조건이 계속
   참이어도 5~10분 주기 cron이 돌 때마다 동일 스탑에 대해 중복 알림이 쌓이는 것을 막기 위함).
   사용자가 응답(Yes/No)하면 그 row는 proposed가 아니게 되므로, 조건이 여전히 유효하면 다음 주기에
   새 제안이 다시 생성될 수 있다 (원치 않으면 "같은 조건 재발생 시 알림 안 함" 옵션은 11.4절에서 검토).
5. 그 날짜의 스탑 배열에서만 교체 후 2-opt 재실행 (해당 날짜만, 표본이 작아 즉시 처리 가능)
6. (선택) 교체된 스탑만 LLM 내레이션 갱신 — 나머지 날짜의 기존 내레이션은 그대로 둠

> 매니징 예시 문구 형태("비가 옵니다, [야외 스탑] 대신 [대체 장소]로 변경할까요?" — 장소명은 예시,
> 실제 데모 문구는 시드 데이터의 실제 POI명으로 채움, 8장/11.5절)가 정확히 이 경로다 —
> 질문형인 이유가 여기 있다. 알림은 항상 "제안"이지 이미 적용된 변경사항이 아니다. `alerts` payload와
> API 설계도 "이미 바뀐 스탑"이 아니라 "바뀌자고 제안하는 스탑" 단위 (API_CONTRACT.md 3장).
>
> **상황별 카테고리 조정표 (전 항목 확정)**
>
> | condition | 처리 방식 |
> |---|---|
> | rain | ① nature_hiking, leisure_sports, festival_event 태그를 **가진 POI를 후보 풀에서 아예 제외** ② 남은 후보에 대해 원래 가중치 그대로 스코어링 |
> | traffic (혼잡) | 카테고리 조정 아님 — 거리 기준 후보 재선정 (아래 별도 설명) |
> | festival_cancelled | 해당 festival_event POI 1건만 후보에서 제외 (다른 카테고리는 영향 없음) |
>
> **rain은 "가중치 0"이 아니라 "후보 제외"다 (수정 — 1주차 아키텍처 점검에서 발견)**: 가중치만 0으로
> 낮추면, 태그를 여러 개 가진 POI(예: `["nature_hiking","food_local"]`)가 남은 `food_local` 점수로
> 여전히 1위가 될 수 있다 — 즉 "비 오니까 등산 대신"이라고 알림을 보내놓고 다른 야외 스탑을 제안하는
> 상황이 생긴다. 실제로 자유텍스트 없이 생성한 코스는 모든 가중치가 0이라(API_CONTRACT.md §1) 전부
> 동점이 되어 DB 순서대로 아무거나 뽑히기까지 한다. 그래서 rain은 **태그 기반 제외 필터가 먼저**이고,
> 가중치는 남은 후보의 순위를 매기는 데만 쓴다. (시드 데이터는 POI당 태그가 1개씩이라 이 차이가
> 드러나지 않지만, 실제 TourAPI 데이터가 들어오면 바로 문제가 된다.)
>
> **traffic(혼잡) 상세 로직 (확정)**: 카테고리 가중치는 건드리지 않고, 지금 위치에서 가까운 후보만
> 남기는 거리 필터를 먼저 적용한 뒤 그 안에서 기존 `preference_weights`로 순위를 매긴다.
> - **감지 기준**: 다음 스탑까지의 구간 이동시간(카카오모빌리티 Directions API `duration`, 이미 동선
>   표시용으로 호출 중인 것을 재사용 — 3장)이 **1시간을 넘으면** 혼잡으로 판단해 트리거. 산간 지형
>   특성상 기준선 이동시간 자체가 긴 경우가 많아, 느슨하게 잡아 오탐(단순히 산길이라 오래 걸리는 것을
>   혼잡으로 잘못 판단하는 것)을 줄인다. 별도 교통 API는 쓰지 않는다(제안서의 교통안내서비스는 §2.3에서
>   이미 제외 — 동선 표시용 API의 실시간 duration으로 충분히 대체됨).
> - **대체 후보 탐색 반경**: 현재 위치에서 이동시간 15분 이내(직선거리 대신 이동시간 기준 — 산간이라
>   직선거리와 실제 도달 가능성이 안 맞을 수 있음). 같은 날짜·같은 시군, 이미 코스에 쓰인 POI 제외
>   조건은 부분 재구성 로직(위 2~3단계)과 동일.
> - 이 값들(1시간 / 15분)은 실제 서비스로 확장될 때를 대비한 기준이고, 데모 심사 중 보여주는 트리거는
>   `POST /api/alerts/trigger`로 수동 발동하므로(API_CONTRACT.md §3) 이 임계값이 데모 진행에 영향을
>   주지 않는다.

> 이유: 매 요청마다 LLM이 전체 코스를 추론하면 지연시간과 비용이 크게 증가함.
> LLM은 입력 파싱과 출력 설명 등 "짧은 입출력" 작업에만 사용. 날짜·인원처럼 형식이 명확한 값까지
> LLM에게 맡기면 오탐(잘못된 파싱) 위험만 늘어나므로 폼으로 직접 받는다.
>
> `relationship` enum (초안, 필요시 조정): `couple` | `family_with_kids` | `friends` | `solo` | `group`
>
> **카테고리 마스터 목록 (확정 — API JSON 스키마·데이터 모델에 이미 하드코딩돼 있어 실질적으로
> 고정됨. 이후 변경은 "검토 후 확정"이 아니라 스키마·동기화 매핑·프론트 표시까지 함께 손대야 하는
> 브레이킹 체인지로 취급할 것. `pois.tags[]`가 반드시 이 키만 사용해야 LLM 가중치와 실제 POI 태그가
> 어긋나지 않는다)**:
> `nature_hiking`(자연/등산 — 전망·경관 좋은 코스도 여기 포함), `onsen_wellness`(온천/웰니스),
> `culture_history`(문화/역사), `food_local`(로컬 미식), `festival_event`(축제/이벤트), `shopping`(쇼핑),
> `leisure_sports`(레포츠/액티비티 — 스키·래프팅·짚라인 등). 가중치는 항목별 0.0~1.0 독립 점수
> (합이 1일 필요 없음 — 등산도 온천도 둘 다 높을 수 있음).
>
> **개수·범위를 이렇게 정한 이유**: 데모가 3개 시군만 다루는 만큼 시군당 POI 표본이 적어서, 카테고리를
> 더 세분화해도(예: 포토스팟을 별도 카테고리로) 표본 부족으로 유의미한 차별화가 안 될 가능성이 높다.
> `photo_scenic`을 별도 카테고리로 두는 대신 `nature_hiking`에 흡수한 이유도 이것 — `leisure_sports`는
> TourAPI가 이미 별도 콘텐츠 타입으로 제공해 매핑 비용이 거의 없고 평창 스키장 특화 스토리(11.5절)와도
> 바로 연결되어 우선 채택. 가중치 범위(0~1)는 그대로 유지 — 범위 자체는 표현력에 문제가 없고, 실제
> 리스크는 LLM이 미세한 소수점 차이를 일관되게 만들어내지 못할 가능성이다. 1주차에 QA팀이 동일 입력을
> 여러 번(5회 이상) 넣어 가중치 출력 편차를 확인하고, **카테고리별 최대값-최소값(편차)이 0.2를 넘으면**
> "낮음/보통/높음/매우높음" 같은 이산 단계로 낮춰 서버에서 고정값(0.2/0.5/0.75/1.0)으로 매핑하는 방식으로
> 전환한다 (`TEST_PLAN.md` T-101 항목 — 기준값 0.2를 판단 근거로 사용). 0.2로 정한 이유: 최종 스코어링에서
> 상위 후보 순위가 실제로 뒤바뀔 만한 크기(체감 가능한 차이)이면서도, LLM 특성상 완전히 동일한 값을
> 매번 재현하기는 어렵다는 점을 감안한 실용적 기준 — 1주차 실측 후 필요하면 조정.
>
> **주의**: 제안서 3)절은 이 파이프라인을 "강원 관광 지식그래프 구축 → 그래프 탐색 + TSP"로 설명한다.
> 새 그래프 DB를 별도로 구축하지 않는다 — 발표·Q&A에서는 "관광지·축제·교통·숙박 간 관계를
> DB 조인/클러스터링으로 표현한 것이 곧 지식그래프"라고 설명을 통일한다.

## 3.6 에이전트 두 종류 (이름이 비슷하니 혼동 주의)

| 구분 | 정적 데이터 수집 에이전트 | 실시간 조건 감시 에이전트 (매니징) |
|---|---|---|
| 담당 팀 | 백엔드팀 | 백엔드팀 |
| 대상 | TourAPI, 의료관광정보 등 공공 API POI/부가 데이터 | 기상청/교통/축제 실시간 데이터 |
| 주기 | 하루~일주일 단위 배치 | 5~10분 단위 |
| 역할 | DB를 채우는 동기화 작업 (코스 생성 알고리즘이 조회하는 원본) | 활성 일정 감시 후 대안 일정 제안(매니징) |
| 스캔 대상 | 전체 지역 POI | `itineraries.status='active'` AND 오늘이 `start_date`~`end_date` 사이인 row만 (4장) |

**알림 무응답 타임아웃 (확정)**: 사용자가 제안(`status: proposed`)에 3분 안에 Yes/No 응답을 하지 않으면
자동으로 `dismissed` 처리한다(적용 안 함 — 4장 status enum과 동일 값 재사용, 새 상태값 추가 없음).
새 cron을 따로 안 두고, 위 실시간 조건 감시 에이전트가 5~10분 주기로 도는 김에 "생성된 지 3분 넘은
`proposed` 알림"도 같이 정리한다 — 정확히 3분째에 칼같이 전환되진 않고 다음 cron 주기에 정리되지만
(최대 수 분 오차), 데모 규모에서는 문제없는 수준. **타임아웃이 필요한 이유**: 매니징 중복 방지 로직
(3.5절)이 "같은 스탑에 대해 `proposed` 알림이 이미 있으면 새로 안 만든다"는 규칙이라, 응답 안 된 알림이
영원히 `proposed`로 남으면 나중에 같은 조건이 다시 발생해도 새 알림이 안 가는 문제가 생기기 때문.

## 3.7 LLM 모델 선택 전략

- **벤더: Claude API (확정)**. 검토 시점 기준 순수 토큰 단가·토큰 효율(같은 텍스트를 더 적은 토큰으로
  인코딩하는 정도)만 보면 OpenAI 소형 모델 쪽이 다소 유리했지만(입력 단가 약 25%, 출력 약 10% 저렴,
  중국어 텍스트 토큰 수 약 26% 적음), 이 프로젝트는 매 요청마다 카테고리 마스터 목록·JSON 스키마 같은
  고정 텍스트를 반복 전송하는 구조라(3.5절) Anthropic의 프롬프트 캐싱(캐시 히트 시 입력 90% 할인)을
  활용하면 그 격차가 좁혀진다고 판단. 3주 데모 규모의 실제 호출량에서는 어느 쪽이든 절대 비용 차이가
  크지 않아, 비용보다 팀의 기존 사용 경험을 우선해 Claude API로 확정.
- **데모 단계**: 파라미터 추출·내레이션은 복잡한 추론이 필요 없는 작업이므로,
  가장 비싼 플래그십 모델이 아니라 가볍고 빠른 티어(Haiku급)를 우선 사용 (비용·응답속도 모두 유리).
- **향후 로컬 LLM 전환**: 지금 확정하지 않는다. 로컬은 트래픽이 꾸준히 많고 이를 운영할
  MLOps 인력이 있을 때만 상용 API보다 유리하다 (GPU 서버 고정비 vs 종량제 비교).
- **액션 아이템**: 데모 기간부터 LLM 호출 횟수·토큰 사용량·응답 지연시간을 로그로 남길 것.
  향후 전환 여부는 이 실사용 데이터를 근거로 손익분기점을 계산해서 결정한다.

## 3.9 간편 로그인 전략 (신규 — 게스트 세션 문제 해결)

DB/Realtime을 이미 Supabase로 쓰고 있으므로, 별도 OAuth 서버를 새로 만들지 않고 **Supabase Auth**의
소셜 로그인 기능을 그대로 쓴다.

- **데모 구현: Google 로그인만.** Supabase가 기본 제공하는 provider라 OAuth 클라이언트 발급 +
  대시보드 설정만으로 반나절 내 연동 가능. 타겟(외국인 관광객) 커버리지도 가장 넓다.
- **Apple/Naver는 이번 스프린트에서 구현하지 않는다.** Apple은 유료 Apple Developer Program 계정이
  전제조건이라 팀 보유 여부가 불확실했고, Naver는 Supabase 기본 provider가 아니라 커스텀 OIDC 등록이
  필요해 공수가 더 든다. 둘 다 시간 대비 이득이 낮다고 판단해 제외. 필요해지면 2단계(Scale-up)에서 추가.
- **로그인 실패·거부 시 폴백 (확정): 재시도.** 단, 자동 재시도가 아니라 에러 메시지 + "다시 시도" 버튼
  형태로 구현한다 — 팝업을 프로그램이 사용자 동작 없이 자동으로 다시 열면 브라우저 팝업 차단에 걸릴 수
  있어서, 사용자가 버튼을 눌러야 Google 로그인 팝업이 다시 뜨도록 한다. 이 과정에서 게스트 상태로
  만들어둔 코스 데이터(클라이언트 메모리 보관, 위 문단)는 로그인 재시도 여부와 무관하게 유지되어야
  한다 — 로그인에 여러 번 실패해도 사용자가 만든 코스가 사라지면 안 됨.

> 로그인 전(게스트) 상태에서는 서버에 `users` row를 만들지 않는다 — 코스 데이터는 클라이언트 상태로만
> 보관하고, "저장" 클릭 시 Google 로그인 완료와 동시에 `users`+`itineraries` row를 생성한다. 이렇게
> 하면 4장의 "게스트 세션 발급 방식" 문제 자체가 없어진다 (11.4절 갱신).
>
> **`users` row 생성 방식**: Supabase Auth 자체는 `auth.users`라는 별도 내부 테이블을 자동으로 관리하지만,
> 이 프로젝트가 쓰는 위 `users`(public 스키마, id/preferred_lang/auth_provider)는 별개의 앱 테이블이다.
> 저장 API(`POST /api/itineraries`, API_CONTRACT.md 2장)가 요청의 Supabase 인증 토큰을 검증해 `auth.uid()`를
> 얻고, 그 id로 `public.users`에 upsert(없으면 생성, 있으면 그대로) 한 뒤 같은 트랜잭션에서 `itineraries`
> row를 만든다 — 프론트가 별도로 "회원가입" API를 호출할 필요 없음.

## 4. 데이터 모델 (초안 — 개발 중 이 섹션을 계속 갱신할 것)

```
users
  - id, created_at, preferred_lang, auth_provider(google)   # 로그인(저장) 시점에만 생성, 3.9절

itineraries (활성 일정)
  - id, user_id, region_codes[], start_date, end_date, companions, relationship, status, itinerary_json,
    preference_weights
    # region_codes[]: 데모 범위에선 항상 1개만 담김(3.5절 — 시군 단일 선택, 필드는 배열로 확장 대비)
    # companions/relationship: 코스 생성 시 입력받은 구조화 값 그대로 저장. 매니징 자동 교체·수동
    # 편집의 부분 재구성(3.5절)이 relationship 필터를 다시 적용할 때 여기서 읽어옴
    # preference_weights: 코스 생성 시 LLM이 뽑은 7개 카테고리 가중치(3.5절)를 그대로 저장.
    # 매니징 자동 교체·수동 편집(텍스트 없이 "다시 추천")이 재사용 — 매번 다시 LLM을 부르지 않음
    # status enum: draft(저장 전 게스트 상태 — 서버 row 자체가 없어 실제로는 안 쓰일 수 있음, 3.9절 참고)
    #   | active(저장 완료, 매니징 감시 대상) | completed(end_date 지남, 감시 제외) | cancelled(사용자 삭제)
    #   실시간 조건 감시 에이전트(3.6절)는 status='active' AND 오늘 날짜가 start_date~end_date 사이인
    #   itineraries만 스캔 대상으로 삼는다 (여행 중이 아닌 일정까지 매번 스캔하지 않기 위함)

pois (장소 데이터, TourAPI 동기화)
  - id, content_id, region_code, name, category, lat, lng, tags[], event_start_date, event_end_date,
    synced_at, adult_only
    # content_id(신규 — 1주차 아키텍처 점검 후속): TourAPI가 부여한 콘텐츠 ID. **재동기화 시 이 값을
    # 키로 upsert해서 `id`(uuid)가 유지되도록 한다.** 기존 방식(delete 후 insert)은 매번 새 uuid를
    # 발급하는데, itineraries.itinerary_json은 스냅샷으로 옛 poi_id를 들고 있어서(위 스냅샷 정책)
    # 동기화 한 번에 매니징 에이전트의 pois 재조회가 0건이 되고 rain 트리거가 로그 없이 영구
    # 무동작이 된다. 시드 데이터에도 임의의 content_id를 부여해 같은 규칙을 적용
    # tags[]는 반드시 3.5절 카테고리 마스터 목록의 키만 사용 (LLM 가중치 출력과 동일한 값 체계 유지)
    # event_start_date/end_date는 festival_event 태그를 가진 row에만 값이 있음(그 외 NULL). TourAPI의
    # 축제/공연/행사 콘텐츠 타입에 이미 포함된 필드를 그대로 매핑 — 별도 API 불필요
    # adult_only(boolean, 신규 — 1주차 백엔드 구현 중 추가): 3.5절 "family_with_kids면 성인 전용 성격
    # POI 태그 제외" 필터용. tags[]는 7개 카테고리 키 고정이라 이 값을 태그로 표현할 수 없어 별도
    # 컬럼으로 분리. relationship 필터가 family_with_kids일 때 이 값이 true인 POI를 후보에서 제외

care_facilities (여행 케어 안내용 정적 데이터, 신규 — 1주차 백엔드 구현 중 추가)
  - id, content_id, region_code, name_en, name_zh, category(hospital/pharmacy 등), phone, address_en,
    address_zh, lat, lng, synced_at
    # GET /api/care(API_CONTRACT.md §4)가 그대로 반환하는 정적 큐레이션 데이터. pois와 별개 테이블로
    # 분리한 이유: 여행 케어 안내는 로그인/코스와 무관하게 항상 조회되는 정적 목록이라(2.1절), 코스
    # 생성 스코어링 대상인 pois와 성격이 다름. 시드 데이터는 8장 참고 — 병원 전화번호는 119를 제외하고
    # 실제 서비스키로 sync_medical.js 실동기화 전까지 null로 비워둠(잘못된 응급연락처 노출 방지)
    # name_en/name_zh, address_en/address_zh (수정 — 1주차 아키텍처 점검 후속): 출처인 의료관광정보
    # 서비스(MdclTursmService)가 langDivCd로 ENG/JPN/CHS/RUS만 제공하고 **한국어 응답이 아예 없다**.
    # 단일 name 컬럼으로는 담을 수 없어 언어별로 분리하며, 동기화는 같은 지역을 ENG·CHS 두 번 호출해
    # content_id 기준으로 같은 row에 합친다. 6장 "모든 사용자 대면 텍스트는 다국어 키 기반" 원칙과도 일치

alerts (매니징 트리거 로그)
  - id, itinerary_id, trigger_type(weather/traffic/festival), condition, triggered_at,
    status(proposed/confirmed/dismissed), day, previous_poi_id, proposed_poi_id, responded_at
    # status: proposed = 알림만 보낸 상태(아직 itinerary_json 안 바뀜), confirmed = Yes 눌러서 적용됨,
    # dismissed = No 클릭 또는 3분 무응답 타임아웃(3.6절, cron이 자동 전환 — 이 경우 responded_at은 NULL로
    # 남겨 "사용자가 실제로 응답한 것"과 구분). proposed_poi_id는 3.5절에서 미리 계산해둔 대체 후보(적용 전)
```

> 에이전트가 새 테이블을 만들기 전, 반드시 이 섹션에 먼저 추가하고 팀에 공유할 것.
>
> **`itinerary_json` 스냅샷 정책 (확정)**: `itinerary_json` 안의 스탑마다 `poi_id`가 들어있지만
> DB 레벨 FK는 아니다(JSONB 값). 코스 완성 시점의 스냅샷(이름/좌표 등)을 그대로 유지하며, 표시할 때
> `pois`와 다시 조인해 최신화하지 않는다 — 여행 기간이 짧고(2~4일) `pois` 필드들이 실시간성 정보가
> 아니며, 매니징/수동 편집이 어차피 변경 시점마다 최신 `pois`로 재스코어링해 다시 스냅샷을 남기므로
> 별도 조인이 필요 없다(3.5절). 상세 근거는 `ERD_SEQUENCE.md` §1 참고.

| 카카오모빌리티 Directions API (자동차 길찾기) | 코스 저장/부분 재구성 시 확정된 순서의 실제 동선·이동시간 표시 (3장) — 순서 자체는 서버 Haversine 계산이라 이 API에 의존하지 않음 | 서버 사이드, 인접 스탑 1:1 호출(다중경유지 미사용). 무료 쿼터 1만 건/일 |
| LLM API | 코스 파라미터 추출, 영/중 내레이션 | 서버 사이드에서만 호출 (API 키 노출 금지) |

> 제안서 3)절에 나열된 나머지 API(다국어관광정보서비스, 자연관광정보, 교통안내서비스, 반려동물/육아)는

> 추가하지 않고, TourAPI 자체의 축제/공연/행사 콘텐츠 타입(행사 시작·종료일 필드 포함)을 그대로 동기화해
> 사용한다** — `festival_event` 카테고리(3.5절)를 위한 데이터는 이걸로 충분하다.

## 6. 비기능 요구사항

- 반응형: 모바일(~768px 미만) 지도 중심 + 바텀시트 / 데스크톱(768px 이상) 좌측 리스트+우측 지도
- **위치 기반 기능 폴백 (수정 — 기존 "QR로 세션 이어보기"는 게스트 세션 모델과 모순돼 폐기)**: SOS 버튼
  자체는 `tel:119` 다이얼만 여는 거라 위치 정보가 애초에 필요 없다(2.1절). 위치가 실제로 쓰이는 곳은
  여행 케어 안내 화면에서 가까운 순으로 정렬해 보여주는 부분인데, `navigator.geolocation` 미지원/거부
  시엔 정렬 없이 선택된 시군(코스의 `region_codes[0]`, 배열이지만 값은 항상 1개 — 3.5절) 기준 정적 리스트를 그냥 순서
  그대로 보여준다 — 별도 안내 화면이나 세션 이어받기 개념 자체가 필요 없음
- 페이지 로드 3초 이내, 코스 생성 응답 3초 이내
- 모든 사용자 대면 텍스트는 다국어 키 기반으로 작성 (하드코딩 금지) — 매니징 알림 문구도 포함이다.
  알림 message는 서버가 완성된 문장을 하드코딩해 내려보내지 말고, 다국어 키 + 치환값(장소명 등)
  형태로 내려보내 프론트가 조립한다 (API_CONTRACT.md §3)
- **날짜·시각 기준은 전부 KST(Asia/Seoul) (신규 — 1주차 아키텍처 점검에서 발견)**: `start_date`/
  `end_date`, "오늘이 여행 기간 안인가" 판정, 축제 기간 비교, 기상청 `base_date`/`base_time` 계산이
  모두 한국 날짜 기준이다. 서버는 UTC 환경(Railway/Render 기본값)에 배포되므로, "오늘"을 구할 때
  `toISOString()`처럼 UTC로 떨어지는 방식을 쓰면 9시간 어긋난다 — 한국 새벽 0~9시 사이에 조건 감시
  에이전트(3.6절)가 전날 일정을 스캔하거나, 당일치기 일정이 감시 대상에서 통째로 빠지는 조용한 실패가
  생긴다. 날짜를 만들거나 비교하는 모든 코드는 명시적으로 KST로 변환한 뒤 계산할 것
- **외부 API 실패 시 폴백 UX (확정 — 원칙: 실패한 조각만 조용히 대체, 핵심 경험은 절대 막지 않음)**
  - TourAPI: 배치 동기화라 사용자 화면에 직접 노출되는 실패가 아님. 그날 동기화가 실패해도 DB의
    마지막 성공 데이터를 그대로 사용(자연 폴백). 연속 실패는 사용자 UX 문제가 아니라 백엔드팀 운영
    이슈 — 재시도 로직 + 실패 시 `HANDOFF_LOG.md` 기록
  - LLM 파라미터 추출: API_CONTRACT.md 1장에 기 확정 — 1회 재시도 후에도 실패하면 가중치 전부 0 +
    `activity_level: medium`으로 코스 생성 계속 진행(에러로 막지 않음)
  - LLM 내레이션: 실패 시 해당 문장을 생략하고 나머지 코스 카드는 그대로 표시. 완전히 비우기 아쉬우면
    언어별 고정 문구 1개(하드코딩, 다국어 키 예외)로 대체 가능
  - 카카오맵 SDK 로드 실패: 빈 화면 금지(`TEST_PLAN.md` B-001) — 지도 자리를 텍스트 기반 스탑
    리스트(장소명·주소 순서대로 나열)로 대체하고 "지도를 불러올 수 없습니다 · 새로고침" 안내 + 재시도
    버튼 표시
  - (선택, 시간 남으면) 데모 시연 중 라이브 API 불안정 리스크 대비 — 강제 트리거 버튼 등 리허설로
    고정된 시나리오는 데모 모드에서 로컬 캐싱된 "알려진 성공 응답"을 우선 사용하는 안전장치 고려.
    3주 일정상 필수 아님, 여유 있을 때만
- Google 로그인 실패·거부 시 폴백: 확정 — 재시도 버튼 방식, 게스트 코스 데이터 유지 (3.9절)
- 매니징 알림 무응답 타임아웃: 확정 — 3분 후 자동 dismissed (3.6절)
- **Realtime 채널은 itinerary 단위로 구독한다** (`alerts:itinerary_id=eq.{id}`) — 전체 사용자에게
  브로드캐스트하지 않는다. 다른 사용자의 매니징 알림이 섞여 들어오면 안 됨 (API_CONTRACT.md §3 근거 조항)
- **RLS (Row Level Security, 신규 — 1주차 백엔드 구현 중 추가)**: `users`/`itineraries`/`alerts`에 본인
  소유 row만 SELECT 가능한 정책 적용. 위 Realtime 요구사항(다른 사용자 알림이 섞이면 안 됨)의 DB
  레벨 방어선 — 애플리케이션 코드 버그로 채널 필터가 뚫려도 DB 자체가 막아줌
- **CORS**: 백엔드(Railway/Render)는 프론트 배포 도메인(Vercel)과 로컬 개발 주소만 허용 origin으로 등록.
  구체적 도메인 값은 배포 확정 후 `.env`에 기록 (API_CONTRACT.md §0)

> 7개 카테고리(3.5절)에 골고루 분산해 수기로 채운 `pois` 시드 데이터를 만들어 공유한다 — `festival_event`

> (11.5절)는 "비가 옵니다, [야외 스탑] 대신 [대체 장소]로 변경할까요?" 형태만 고정이고, "오대산 등산"/
> "평창 알펜시아"는 예시일 뿐 반드시 이 이름이어야 하는 건 아니다. 시드 데이터에 실제로 넣은 POI
> 중에서 우천 시 부적합한 야외 스탑 1곳 + 대체 가능한 실내/다른 카테고리 스탑 1곳을 아무 시군에서나
> 골라 확정하고, 그 실제 이름으로 11.5절/API_CONTRACT.md §3 예시/`TEST_PLAN.md` 리허설 스크립트를
> 다 같이 갱신하면 된다. 다만 "이 두 곳이 시드 데이터에 실제로 있는가"는 1주차에 확인해둬야 한다 —
> 3주차 리허설 때 가서 "그 장소가 데이터에 없네" 하고 처음 발견하면 늦기 때문.
>
> **LLM 가중치 이산화 결정 기한 (신규)**: `TEST_PLAN.md` T-101(가중치 출력 편차 실측, 0.2 기준값)은
> 1주차 후반까지 QA팀이 끝내고, 그 결과로 연속값(0~1)을 그대로 쓸지 이산 단계(0.2/0.5/0.75/1.0)로

## 10. 다중 에이전트 협업 프로토콜 (신규)

여러 Claude Code 세션(프론트/백엔드/QA)이 이 저장소의 `docs/` 문서를 동시에 참조하는 구조에서,
같은 파일에 여러 팀이 동시에 쓰면 나중에 쓴 세션이 앞선 변경을 덮어쓰는 문제가 생긴다. 이를 막기 위해
"다중 리더, 단일 라이터" 원칙을 적용한다.

- **읽기**: 모든 팀 세션은 `docs/GANGWON_GO_PRD.md`, `docs/API_CONTRACT.md`, `docs/TEST_PLAN.md`, `docs/HANDOFF_LOG.md`를 항상 읽을 수 있다.
- **쓰기**: `docs/GANGWON_GO_PRD.md`는 전략기획팀(PM)만 쓴다. `docs/API_CONTRACT.md`는 백엔드팀이 제안하고 PM이 반영한다. `docs/TEST_PLAN.md`는 QA팀이 제안하고 PM이 반영한다.
- **핸드오프**: 각 팀 세션은 작업을 마칠 때 `docs/HANDOFF_LOG.md`에 아래 형식으로 append만 한다 (기존 내용을 덮어쓰지 않음).

  ```
  ## [YYYY-MM-DD HH:MM] 팀명
  - 변경: (무엇을 했는지)
  - 블로커: (막힌 것, 없으면 "없음")
  - 다음 액션: (다음 세션이 할 일)
  ```

- PM은 `docs/HANDOFF_LOG.md`를 확인해 필요한 변경을 `docs/GANGWON_GO_PRD.md` / `docs/API_CONTRACT.md` / `docs/TEST_PLAN.md`에 반영하고, 반영 후 팀에 공유한다.
- git은 팀별 feature 브랜치(`feat/frontend-*`, `feat/backend-*`, `feat/qa-*`)로 작업하고, `docs/API_CONTRACT.md` 변경은 반드시 해당 백엔드 PR과 같은 커밋에 묶는다.

## 11. 제안서 정합성 노트 (신규)

이 절은 공모전 제출용 제안서(PDF)와 이 PRD의 실행 범위 사이 표현 차이를 팀이 같은 언어로
설명할 수 있도록 정리한 것이다. 발표·Q&A 준비 시 반드시 참고할 것.

### 11.1 언어 지원 (프레이밍으로 해결)

제안서는 "6개 언어 100% 커버"를 차별점으로 명시했지만, 데모는 영/중 2개 언어만 실제 구현한다.
추가 구현(정적 번역 콘텐츠 통합 등)은 일정상 하지 않기로 결정했다. 발표 시에는 "다국어관광정보서비스
등 공공 API가 이미 6개 언어 원문 데이터를 제공하므로, 지금 보여드리는 영/중 파이프라인을 그대로
나머지 언어에 연결하는 것이 다음 단계"라는 방식으로 설명한다. 즉 "왜 6개 언어가 아직 안 되냐"가
아니라 "확장 경로가 이미 확보돼 있다"는 프레임으로 답변을 통일한다.

### 11.2 강원 18개 시군 커버리지 (프레이밍으로 해결)

제안서 로드맵 표는 "1단계 MVP(2026) = 강원 18개 시군"으로 명시했지만, 데모의 라이브 시연은
인제·홍천·평창 2~3개 시군에 집중한다(2.3절, out of scope 유지). 데이터 자체를 18개 시군으로
확대하지 않기로 했으므로, 발표 시에는 "지금 보여드리는 3개 시군은 1단계 MVP의 시작점이며,
같은 파이프라인으로 나머지 15개 시군까지 확장하는 것이 다음 단계"라는 방식으로 설명한다.
**팀 전체가 이 표현으로 통일해서 답변할 것** — 시군마다 다른 설명이 나오면 정합성 문제가 부각된다.

### 11.3 세부 기능 격차 (전면 제외)

산간 GPS 자동 구조신호, 알레르기 자동 필터링, 보험 청구, 영사관 정보, 식사/숙박 코스 자동 삽입,
환승시간 자동 계산은 제안서엔 있지만 이번 데모엔 목업조차 만들지 않는다. 발표자료 로드맵 슬라이드에
"2단계(Scale-up, 2027~2028) 확장 항목"으로만 나열하고, 라이브 데모 화면에는 노출하지 않는다.
심사위원이 물으면 "데모 범위 밖, 2단계 로드맵"이라고 짧게 답하고 넘어간다.

### 11.5 데모 시나리오와 제안서의 시너지 (참고)

제안서의 강원 특화 카테고리(소도시 인제·홍천, 스키장 평창, 지역축제 홍천강 꽁꽁축제)가 데모
대상 시군과 겹친다. 데모 코스 예시에 이 요소를 의도적으로 포함하고, 매니징 트리거 시연 문구는
제안서의 질문형 톤("비가 옵니다, [야외 스탑] 대신 [대체 장소]로 변경할까요?" 형태)을 그대로 살린다 —
"오대산 등산"/"평창 알펜시아"는 제안서에 나온 예시일 뿐, 실제 데모 문구는 팀이 확정한 시드 데이터의
실제 POI명으로 채우면 된다(8장 — 1주차에 미리 확정).

### 11.6 예상 심사 질문 대응 (발표 화법)

  서버에서 감시하는 방식입니다 — 날씨·교통 등 조건이 바뀌면 코스가 여전히 유효한지 주기적으로

  백그라운드 위치 추적이 불안정하다는 점도 고려한 설계입니다. 다만 지도에서 내 위치를 보면서
  이동하는 건 별개 기능으로 지원합니다 — 화면에 표시만 하는 거라 서버가 위치를 저장하지 않고, 앱을
  보고 있는 동안 실시간으로 갱신됩니다." (3.5/3.6절, 2.1절 지도 기능)
